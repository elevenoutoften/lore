# Task: flow_000877 — Release per-thread SQLite connections to avoid thread-pool connection leak

## Context

`LedgerDB` gives each thread its own `sqlite3.Connection` via `threading.local` (ledger.py:108, 136-148). However `LedgerDB.close()` (ledger.py:1933-1937) only closes the CALLING thread's connection — connections opened on threadpool worker threads are never explicitly closed and leak until garbage collection.

This is a resource hygiene gap (not a correctness bug — all current `close()` call sites are single-threaded CLI/test teardown). But it matters for a long-lived server with many worker threads.

## Current Code

`ledger.py:105-148`:
```python
class LedgerDB:
    def __init__(self, db_path: Path):
        self.db_path = Path(db_path)
        self._tl = threading.local()
        self._conn_lock = threading.Lock()
        ...

    @property
    def connection(self) -> sqlite3.Connection:
        conn = getattr(self._tl, "conn", None)
        if conn is None:
            with self._conn_lock:
                conn = getattr(self._tl, "conn", None)
                if conn is None:
                    ...
                    conn = sqlite3.connect(self.db_path, check_same_thread=True)
                    ...
                    self._tl.conn = conn
        return conn
```

`ledger.py:1933-1937`:
```python
def close(self) -> None:
    conn = getattr(self._tl, "conn", None)
    if conn is not None:
        conn.close()
        self._tl.conn = None
```

`recall_claims` docstring (ledger.py:1166-1177) says "Semantic scoring is capped to the strongest 50 candidates so one recall cannot synchronously re-embed the full 500-row pool." — but this is now stale: `effective_pool` widens to `min(pool_limit * 3, 2000)` when a query is supplied (line 1180-1182). The docstring should reflect this.

## What to Implement

### 1. Track per-thread connections and close them all in close()
File: `lore_app/ledger.py`.

Add a registry of opened connections (e.g. a `WeakSet` or a plain `set`) that tracks all per-thread connections. When `close()` is called, iterate the registry and close every connection, not just the calling thread's.

Implementation approach:
- Add `self._all_conns: set[sqlite3.Connection] = set()` (or `weakref.WeakSet`) to `__init__`
- In the `connection` property, after creating a new connection, add it to `self._all_conns`
- In `close()`, iterate `self._all_conns`, close each connection that's still open, clear the set, and also clear `self._tl.conn`

Use a `weakref.WeakSet` so connections that are garbage-collected before `close()` don't cause errors. Or use a plain set and handle `conn.close()` errors gracefully. Either is fine — pick the simpler one.

### 2. Update recall_claims docstring
File: `lore_app/ledger.py`, `recall_claims` method (line 1166-1177).

Update the docstring to reflect the query-conditional pool widening. The current text says "the strongest 50 candidates so one recall cannot synchronously re-embed the full 500-row pool" — update to mention that the pool widens to ≤2000 when a query is supplied.

### 3. Add test verifying close() releases connections from all threads
File: `tests/test_recall_perf.py` (or `tests/test_recall.py`).

Add a test `test_close_releases_all_thread_connections` that:
1. Creates a `LedgerDB`, initializes it, inserts some claims
2. Opens connections on N worker threads (e.g. 4) using `ThreadPoolExecutor` — each worker calls `ledger.recall_claims(...)` or `ledger.connection` to trigger per-thread connection creation
3. Calls `ledger.close()` from the main thread
4. Asserts no lingering open connections — e.g. all connections in the registry are closed, no `ResourceWarning` is raised

Follow the pattern of `test_parallel_recall_and_access_updates_are_thread_safe` (line 186-225) for the ThreadPoolExecutor setup.
